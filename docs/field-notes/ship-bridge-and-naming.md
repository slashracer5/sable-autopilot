**Avionics controller + ship bridge (how `ship_*` peripherals actually appear)**

Measured on Create: Avionics 0.7.0 / CC: Tweaked 1.120.2 / CC: Sable 1.3.4 / Create Aeronautics 1.3.2 (2026-11-16, on an assembled Sable ship).

- **Connecting the controller (user-verified, this is the usual stumbling block):** the `ship_*` bridge only works when the **networking cable runs directly into the avionics controller block itself**. A wired modem placed on the controller, or the controller attached straight to the computer, gives only the plain 2-method peripheral (`avionics_controller`: `isTransponderOn`, `setTransponder`), i.e. just the transponder, and publishes nothing. Put a wired modem on the **computer** (right-click it so it shows the red ring) and run cable from that network to the controller (cable touching the controller). The computer then lists `ship_*` names through `peripheral.getNames()` / `modem.getNamesRemote()`.
- **The computer must be on an assembled ship** (`sublevel.isInPlotGrid()` is `true`). The controller block must be part of that same ship. On the ground it bridges nothing.
- **Diagnosis when only `avionics_controller_0` (or `avionics_controller`) appears with 2 methods:** the controller is reached through a modem or directly, not by a bare cable. Rewire so a cable (not a modem) touches the controller, then re-scan (the mod rescans every ~2 s). In the first test session this took many rounds because wrenching the controller, re-assembling and adding a velocity sensor were tried before the wiring was changed; the sensor was a coincidence.
- **A block that is both directly on the modem network and on the ship shows up twice**: once under its modem-local name (`avionics_controller_0`, `velocity_sensor_0`) and once as `ship_*`. Rewiring so only the bridge reaches it removes the duplicate. Prefer the `ship_*` name.
- **Bridged blocks**: everything on the ship except computers, turtles, modems and shafts/gears/belts (tag `create_avionics:not_bridged`). Gearshifts, transmissions, creative motors, bearings, sensors, the controller and instruments are all bridged.
- **Name format**: `ship_<type>[_<zone>]_<n>`; the zone (`fore`, `aft`, `port`, `starboard`, `forward`, `lateral`, and compounds such as `fore_starboard`, `aft_starboard`) is derived from where the block sits relative to the ship's **bow**, which is set by the first controller's facing (wrench the controller's side to turn it a quarter). Namespaced blocks keep their id: `ship_create:gearshift_0`, `ship_Create_CreativeMotor_0`, `ship_redstone_transmission_0`.
- **Names are NOT stable.** The same four bearings were `..._fore_starboard_0`, `_aft_starboard_0`, `_port_0`, `_starboard_0` first, then `_fore_0`, `_aft_0`, `_port_0`, `_starboard_0` after a rewire, and `aft` became `aft_starboard_0` after a crash/rebuild. Never hard-code a bearing name in a program: scan `peripheral.getNames()` for the prefix (`ship_gyroscopic_propeller_bearing_`) and map each to a role by a physical test (see the propeller-bearing notes). Also re-read the list after any rewire or bow change.
- **Indices (`_0`, `_1`...) pair up by creation order, not by function.** `ship_redstone_transmission_N`, `ship_create:gearshift_N`, `ship_Create_CreativeMotor_N` happened to belong to the same prop in this build (N = 0 fore, 1 starboard, 2 port, 3 aft) but that was found by powering each transmission and diffing every gearshift and bearing speed, not from the names. Re-derive it for any new build (`cc_exec` snippet: set one transmission to level 1, wait 2 s, diff `getSpeed()` of all gearshifts/bearings, set back to 0).
- **Peripheral count does not matter for reads**: bridged `any`-thread getters are free even with 29 names on the network (see `cc-runtime-and-timing` for the calls that do cost a tick: setters and `sublevel.*`).
- **Other sensors on this ship**: `velocity_sensor` (`getVelocity`, `getAxis`; four of them, `forward_0/1` read axis x, `lateral_0/1` read axis z), `gimbal_sensor` (see below), no altitude/optical/navigation sensors were needed: `sublevel` already provides pose, velocity and mass.
- **Weather instruments** (`thermometer`, `hygrometer`, `barometer`, `rain_gauge`, `almanac`) bridge like any other block; they all have `read()`, `getValue()`, `getUnit()`.
